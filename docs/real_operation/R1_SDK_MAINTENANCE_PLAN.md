## 实际源码发现与新增候选

已核对当前 SDK SHA c4dd48f3…、节点 SHA 4d37d84c…。
原节点 __init__ 会调用 pwm_servo_set_offset(1,0) 和 set_motor_speed(四路零速)；
main 的 KeyboardInterrupt 分支也发送电机零速指令。
整车 bringup 另有 init_pose/action_name=init。
所以“重启原驱动/整车服务”不是本阶段无执行器命令的安全默认方案。

候选保存在 patches/jetrover_readback/，仅生成审核补丁：
1. 新增 readback_maintenance 布尔参数，默认 false，正常模式保留原控制报文字节。
2. 显式维护模式跳过上述启动/中断执行器指令，不创建运动、Torque、PWM等控制订阅。
   只保留原遥测发布、蜂鸣器订阅、受保护的BUS位置服务及原init_finish状态服务。
   旧PWM读取服务不在维护模式中暴露。
3. 在唯一既有 Serial 实例构造时设置有限 write_timeout=0.05s；
   不创建第二端口或第二接收线程，不运行无界 flush/tcdrain。
4. 对这个既有FD调用 TIOCEXCL。它不能撤销已经存在的FD，
   有权限的进程也可能绕过；部署前后仍必须核对所有打开者。
   当前运行端口没有执行该 ioctl。
5. 维护写入复用原CRC函数和完整帧格式，以同一把发送锁串行化。
   仅允许蜂鸣器与指定ID的0x05位置查询帧，运动/扭矩等帧发送前拒绝。
   检查锁预算、整帧写入数及完成期限；I/O、短写或超时故障锁存，不重试。
   软件期限不是硬实时保证，也不证明设备已执行或完成事务。
6. 读取沿用原接收解析器，传递原事务期限；服务失败清除部分结果。
   默认 DISARMED；inner_response_match_verified 前提和 KEY_REUSE_UNSAFE 原样保留。
   维护模式不会自行arm，不能证明连续同ID读回可靠。

本次候选新增的是受限维护环境，不是固件协议修复或可用连续采集器。
正常模式的原控制方法通过AST/字节兼容测试；维护模式主动禁止控制接口。

## 后续部署与回滚审查关口

尚不具备直接执行首次ID1读取的技术条件，也不以软件通过替代单独授权。
下一份实际部署方案必须先补齐：
- 控制板接口/电源/DTR/RTS/重开串口是否导致复位的证据。
- 如何仅管理现有驱动进程而不重启整车初始化、不触发旧main运动分支；
  父launch生命周期、退出信号、自动重启行为须确认。
- 固件身份或厂商针对本车构建的内层ID/命令/长度、重复/迟到边界保证。
- 干净事务epoch、独占前后检查、正常失败停止及回滚后禁止读回的策略。
- 所选完整Git SHA、补丁哈希、原文件备份验证，以及新进程仅暴露维护接口的验收。

得到单独授权后，也只能按审批范围先部署维护模式并被动检查；
首次硬件RPC、重复读取及任何固件操作不由部署授权自动包含。
回滚使用已验证的反向补丁/原文件SHA，不覆盖用户文件。
恢复原驱动本身可能重新发送启动指令，因此不能在本阶段自动回滚重启；
应停止相关操作，按现场监督和另行批准的计划处理。

R2继续复用 RawFeedbackAdapter、RobotStateProvider、RealObservationCore 和 PolicyClient。
Pulse→rad、实际采样时刻与20ms同步证据未满足前，不生成完整Observation或上传伪造state。
